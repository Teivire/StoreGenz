2Sign-in, sessions & RBAC

Every mutation is gated twice: valid active staff first, then a capability resolved live from the role's document — editing a role re-scopes members instantly.

Browser sign-in

app/page.tsx → /api/auth/login → sessions

1
Login screen
Staff picks name + types PIN
2
POST /api/auth/login
Name + PIN checked against staff (must be Active)
3
Session document
sessions row with 30-day expiry; HttpOnly cookie set
4
Client boots
GET /api/auth/session restores identity; all hubs load via refreshAll()
5
Sign out / force-out
DELETE session; /api/security can wipe all sessions (caller survives)

Request gating (every mutation)

lib/db.ts · requireStaff → requireCapability

1
Who is calling?
Cookie pos_session (browser) or X-Staff-Name/Pin headers (scripts)
2
Valid + Active?
No / expired / deactivated → 401
3
Capability check
Role doc resolved live on every request; missing → 403
e.g. sellany Active role — cashiers can sell & refund
e.g. settings.manageAdministrator only — Manager deliberately 403
4
Handler runs
11 capabilities: sell · inventory · purchases · suppliers · customers · finance · register · departments · reports · staff · settings

Activity log
Mutations append to activity_log (best-effort, never blocks)

3Checkout flow (POS → sale)

The heart of the system: cart → validated, policy-enforced, atomic sale with stock decrement and movement-ledger entry.

Happy path

POS hub · New Sale tab

1
Build cart
Product picker (F2 search) or barcode-style SKU; live stock shown
2
Charge (F4)
Payment modal: method (from settings), cash tendered → change, discount %, customer
3
POST /api/sales
Header/cookie auth → capability sell
4
Validate lines
≥1 line, known SKUs, qty ≥ 1, prices snapshotted with product cost
5
Atomic commit
Invoice # from max+1, sale doc + per-product stock $inc:{-qty} + movement entries + loyalty accrual
6
Receipt + refresh
Receipt modal (tax line, footer); client re-hydrates sales & catalog

Policy gates (server-side, live from Settings)

settings → validatePolicy → checkout enforcement

A
Discount cap
discount > maxDiscountPercent% of subtotal → 400 with cap in message
B
Tax
Exclusive: add round(base × rate). Inclusive: divide out rate/(1+rate). Snapshot taxAmount per sale
C
Oversell policy
allowNegativeStock=false → filter stock:{$gte:qty}, short → 409 no partial apply; true → sells through, stock goes negative
D
Credit sales
Payment "Credit" → status Pending (not income) until collected in Customers hub
E
Loyalty
Paid sale to known customer → points $inc floor(total × earnRate); Bronze/Silver/Gold tiers by lifetime points

4Refund flow

Single-shot by design: stock returns once, double refunds conflict at both API and DB level.

Refund steps

Returns & Refunds tab → /api/sales/[id] PATCH

1
Find sale
Search invoice/customer in refundable list (Paid or Pending)
2
Reason
Mandatory reason stored on the sale doc
3
refundSale
Any Active role; guard: status must not already be Refunded
First refundstatus → Refunded · stock $inc:+qty · movements logged · refundedAt stamped
Repeat refundAPI guard → 409 · unique partial index makes a race lose safely
4
Money views update
Dashboard refunds KPI, cash-register expected drawer (by refundedAt window), Payments → Refunds

Concurrency guarantees

verified by npm run verify-concurrency

✓
Distinct invoice numbers
Concurrent checkouts never collide (#INV-n from max+1 inside the write path)
✓
Exact stock decrement
N concurrent sales of qty 1 on stock N → exactly 0 left, no oversell
✓
Single-winner refunds
Racing the same refund → 200 + two 409s, restocked exactly once
✓
Self-cleaning suites
verify-api (41 cases) & verify-concurrency remove their scratch data

5Held / suspended sales

Park a cart mid-transaction without touching stock — resume it on any register later.

Hold → resume → checkout

held_sales collection · /api/held-sales

1
Hold sale (F8)
Cart + optional note (≤140 chars) → POST /api/held-sales → id H-nnn, heldBy, heldAt. No stock deducted.
2
Held / Suspended tab
Any staff can list holds (selling-level gate)
3
Resume
PUT returns the lines and deletes the hold — stock was never taken, so no inventory recheck needed; policy still applies at final checkout
4
Discard
DELETE ?id= drops the hold; sale.hold / resume / discard all logged
5
Finish as normal sale
Resumed cart goes through the standard checkout flow (step 3 above)

6Dashboard analytics flow

One full-history fetch, filtered and aggregated entirely client-side — that's why the date filter responds instantly.

Data → KPIs

refreshAll() → /api/sales?all=1 → Dashboard

1
Hydrate full history
refreshAll() fetches products, sales, staff, settings, roles in parallel (?all=1 = full arrays)
2
Filter chain
Date range (Today/7/30/month/custom/all) → cashier → payment → per-line category. Refunds never count as revenue; Pending isn't income
3
KPIs
Sales, Orders, Refunds, Net sales, Gross profit + margin (profit visible to finance.manage only)
4
Charts & tables
Trend bars with honest zero-fill per day/month, payment mix, top products, staff performance, low-stock list, recent transactions (real createdAt timestamps)
5
Export
CSV / Excel of the currently filtered view; PDF via print

Date-range rules (post-fix)

the "filter not responding" bug, documented

1
Presets
Today · Last 7/30 days · This month · All time — windows computed from local midnight
2
Custom range
From/To date pickers; >45 days auto-switches trend to monthly buckets
3
Empty custom ≠ all-time
Invalid/empty custom range stays empty ($0 / 0 rows) — it used to silently widen to all time, which made the filter look dead
4
Filtering key
Everything filters on createdAt (ISO timestamp), never on the display date string

7Operations: backups, jobs & data integrity

Safety nets run outside the request path so a busy POS night never waits on them.

Backup & restore

scripts/backup-db.js · restore-backup.js · /api/backups

1
Automatic
On boot, instrumentation.ts backs up if the newest file is >24h old (never blocks startup)
2
Scheduled
Windows Task Scheduler "StoreGenz daily backup" runs npm run backup at 02:00
3
Manual / from UI
Settings → Backup & Data → Back-up-now (settings.manage); route spawns the script as a child process (webpack can't interop its CJS imports)
4
Retention
Every backup prunes backups/ to the 30 newest JSON exports
5
Restore
npm run restore -- <file> --yes or UI PUT with confirm phrase; date fields re-typed from ISO strings

Boot & integrity jobs

ensureSeeded · init-db.js · recurring expenses

1
ensureSeeded (once per process)
Creates validators/indexes if missing, seeds roles, ST-001 store, demo staff, settings, sample catalog/sales when empty; failed seed retries instead of 503-ing forever
2
init-db.js (versioned truth)
Idempotent: collMod validators for every collection, full-entry index specs (the spread bug that silently dropped unique is fixed)
3
Movement ledger
Every stock change (sale, refund, adjustment, PO receive/return, transfer) lands in movements so Stock Count reconciles to ledger-net
4
Recurring expenses
Weekly/monthly templates generate real EXP docs on boot (catch-up) and via PUT; nextRun advances
5
Offline behavior
Mongo down → app still boots on seed data with an "offline" banner; writes surface 503, nothing is silently lost
